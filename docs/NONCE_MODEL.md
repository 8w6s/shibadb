# Nonce uniqueness model

ShibaDB's encryption scheme is XChaCha20-Poly1305 with a 192-bit
(24-byte) random nonce per encryption. This document argues, per
crypto subsystem, that nonce collisions cannot occur under the
supported threat model — an assumption that is load-bearing for
the entire AEAD guarantee.

## Threat model recap

The attacker may:

- Modify the on-disk database file, WAL sidecar, and replace
  marker between opens.
- Corrupt any of the above during a live process (WORM DB + hostile
  writable sidecar scenario).

The attacker may NOT:

- Steal the plaintext password.
- Compromise the running process.
- Modify the running process's memory.
- Predict `/dev/urandom` / `getrandom(2)` output.

Under those constraints, the AEAD guarantee is: any successful
`sdb_encrypted_page_decrypt` implies the ciphertext was produced by
this database's `data_key` at some earlier time. Nonce collision
would break that guarantee (two distinct plaintexts under one
(key, nonce) leaks XOR of the plaintexts and reveals the Poly1305
key).

## Per-subsystem argument

### 1. Data-encryption key wrap (`src/key_manager.c`)

The `wrapped_key` field in the superblock is a single ciphertext
encrypting the random 256-bit data key under a password-derived
key. The wrap nonce is:

```
nonce = file_id[16] || wrap_generation_le64[8]
```

- `file_id` is a 16-byte random value generated by `sdb_random_bytes`
  at database creation and never changed (superblock update boundary
  refuses to mutate it).
- `wrap_generation` is a monotonic 64-bit counter starting at 0 that
  the password-rotation code increments on each successful rekey.

Collision would require the same (file_id, wrap_generation) pair to
recur. `wrap_generation` is monotonic-persistent in the superblock;
after a rotation, the new value is durably committed via
`sdb_superblock_store_update_file` before the rotation returns
success. A crash between generation bump and superblock commit
retains the OLD generation on disk, which recovers to the pre-crash
state — no key material was written with an unpersisted generation
because `sdb_key_wrap` is called AFTER the new generation is decided
but BEFORE the superblock write.

`file_id` uniqueness across databases relies on `/dev/urandom` or
`getrandom(2)` — a 128-bit random value has a birthday-safe
collision probability of ~2^-32 at 2^32 distinct databases per
host. That is orders of magnitude past any realistic user
population.

Conclusion: wrap-nonce collision requires either (a) a broken CSPRNG
at DB creation time (nonces derived from a colliding file_id) or
(b) a rollback attack that manages to replay the old superblock
with the same wrap_generation but a different wrapped-key ciphertext
— (b) is caught by the Poly1305 tag verification on the wrap.

### 2. Page-envelope encryption (`src/encrypted_page.c`)

Every page write allocates a fresh 24-byte random nonce via
`sdb_random_bytes` (`sdb_encrypted_page_encode`, line ~65). The
nonce is stored verbatim inside the encrypted payload header (bytes
8..32) — no derivation, no counter, no reuse across pages.

XChaCha20's 192-bit nonce space has a birthday bound of 2^96
distinct encryptions per key before collision probability exceeds
2^-32. At one write per nanosecond on every page in existence for
the lifetime of the universe, the total number of encryptions
would still be far below 2^96.

Conclusion: page-envelope nonces are collision-immune under the
random-nonce assumption. The failure mode reduces to CSPRNG
integrity — which is protected by the hardened `/dev/urandom` open
in `src/random.c` (O_NOFOLLOW + S_ISCHR verification).

### 3. WAL replay (`src/wal.c`)

WAL records contain complete page-image copies. On encrypted DBs,
each page image is already a fully-encoded envelope from the
original commit — the WAL is a byte-for-byte log of ciphertext,
not a re-encryption trigger. Replay writes those bytes to the DB
file without producing new nonces.

Re-replay after a partial crash is idempotent: the same WAL
bytes are re-applied. The nonce inside the envelope is the
original random nonce from the ORIGINAL encryption, replayed
verbatim. No new nonce is generated during replay, so replay
cannot cause collision.

The recovery-time AEAD verification (added post-audit) additionally
refuses to install any envelope whose Poly1305 tag does not verify
under the current `data_key`, closing the WAL-forgery arm of the
threat model.

### 4. Page free + realloc

The audit raised: could a freed page's reallocation produce a
nonce collision with the original encryption? No — every
`sdb_encrypted_page_encode` call generates a fresh 24-byte random
nonce, whether the page is a brand-new allocation or a reuse of a
freed slot. The previous nonce is never consulted; there is no
counter that could reset.

## What would break this model

- CSPRNG returning predictable or repeating bytes. Mitigations:
  hardened `/dev/urandom` open (S_ISCHR + O_NOFOLLOW), preferential
  use of `getrandom(2)` on Linux.
- A future refactor that switches from random nonces to counter-
  based derivation without a corresponding change to the wrap
  generation semantics. Callers implementing such a change must
  update this document and add a dedicated regression test that
  simulates thousands of encrypt-decrypt cycles under a fixed key
  and verifies no nonce repetition.
- Rollback of the superblock to an older wrap_generation without
  restoring the corresponding wrapped_key — the wrap tag catches
  this at load time; the rollback attack surface is bounded by
  the mirror-slot integrity of the two on-disk superblock copies.

## Verification

The following tests exercise the nonce paths (none of them can
prove absence-of-collision at the algorithmic level, but they
verify the structural properties this argument relies on):

- `test_encryption.c` — nonce uniqueness across a sequence of
  encrypt calls under a fixed key; wrong-nonce and wrong-key
  rejection.
- `test_encryption_fault.c` — behaviour under fault injection at
  every stage of the KDF+wrap pipeline.
- `test_coverage_gap.c` — bad-args + partial-block coverage for
  XChaCha20-Poly1305.
- `fuzz/fuzz_xchacha20poly1305.c` and
  `fuzz/fuzz_encrypted_envelope.c` — round-trip fuzz.
- `fuzz/fuzz_wal_recover.c` — attacker-controlled WAL bytes on a
  plaintext harness (extends to encrypted with a data_key seed
  planned for post-1.0).

Anyone modifying `src/xchacha20poly1305.c`, `src/key_manager.c`,
`src/encrypted_page.c`, `src/wal.c` recovery, or `src/random.c`
must confirm this document still holds and either amend it or add
a compensating control.
